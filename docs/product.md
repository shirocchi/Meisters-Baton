# Meister's Baton — ベータの目的と完成条件

更新: 2026-09-07 / 対象: `0.1.0-beta.1`

作業映像だけでは分からない「なぜそう判断したのか」を作業者から引き出し、根拠とともに次の作り手へ渡す。最初の利用者は、数年で担当者が入れ替わる鳥人間・ロボコンなどの学生ものづくりチームである。

## 解く課題

動画や日記が残っていても、止め時、異常の見分け方、材料ごとの判断は作業者の中に残りやすい。既存資料の検索に加え、まだ記録されていない判断を、作業直後の短い対話で残すことを中心に置く。

基本の流れは、**記録 → 判断点を見つける → 質問に答える → 根拠を確認して公開 → 後輩が質問する**。ホームの数字や機能数より、この一周が実際の入力に対して成立することを優先する。

## ベータの利用範囲

- **端末内で使う:** アカウントなしで動画、メモ、回答、技術ページを保存する。途中の記録を再開し、知識を書き出せる。
- **チームで使う:** 設定したAPIへログインし、チームの記録を同期する。更新の競合を黙って上書きしない。
- **AIを使う:** 設定済みの認証付きAPIから映像のサンプルフレームと説明を処理する。映像全体の動作を連続的に理解したと断定しない。
- **AIなしで使う:** 作業者への質問と回答原文から技術ページを作る。AI解析と区別して表示する。
- **サンプルで試す:** 架空の説明用データを明示して一周する。利用者の実記録と区別し、取り込み失敗をサンプル成功に置き換えない。

実装境界とデータ形式は [architecture.md](architecture.md) および `src/domain/types.ts` を正本とする。AI利用、同期、端末配布はそれぞれ設定・接続・検証が必要であり、下表は出荷時に確認する受け入れ条件である。

## 受け入れ条件

| 体験                   | 確認すること                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 記録を残す             | 取り込んだ動画を再生でき、工程名・長さ・回答が再読み込み後も残る。権限拒否や非対応形式から別の入力手段へ戻れる。 |
| 判断を聞き取る         | 工程と質問が結び付き、質問理由が分かる。入力・変更・中断再開が可能。未回答を回答済みにしない。                   |
| 自分の回答を知識にする | その場で追記した固有の判断条件が技術ページに反映され、回答原文に戻れる。                                         |
| 出典を確かめる         | 全ての主要主張に動画・回答・メモの出典がある。存在しない回答ID、映像範囲外の時刻を許さない。                     |
| 確認して公開する       | 生成直後は下書き。人が確認するまで確認済みにならず、編集すると承認が外れる。公開前の確認対象が分かる。           |
| 後輩として尋ねる       | 質問に関連した確認済みの知識へ到達できる。出典不足なら確認が必要と示し、未記録の質問として残せる。               |
| 継続する               | 作業途中の再開、記録の削除、書き出し・復元ができる。同期や読み込みで既存データを黙って破棄しない。               |
| スマートフォンで使う   | 縦画面で主要フローを完走できる。入力欄がキーボードに隠れず、44px以上の主要操作領域とセーフエリアを確保する。     |
| AI・共有の境界を守る   | APIキーはサーバーだけに保持する。チーム外の記録・映像を読めない。通信失敗時も端末内の作業を失わない。            |

## 知識の扱い

主張は手順、判断基準、注意点に分ける。映像に見えた動作と、作業者が説明した理由を同じ証拠として扱わない。「作業者確認済み」は記録の確認状態を表し、工程の安全性や成果物の性能の認証ではない。

例示用の工程説明を汎用の製造指示として使わない。材料の配合、温度、許容値など、元記録にない条件を補わない。素材・設備・対象が異なる場合の判断は、そのチームに確認すべき知識として残す。

実際の工程数、公開数、未回答数から画面を構成する。架空の利用人数、充足率、削減時間、確認者を実績として表示しない。個人Vaultの応募文や実名を製品データへ取り込まない。

## 実利用で評価すること

最初の検証は、利用許可を得た作業動画1本、作業者1人、初めて担当する後輩1人から始める。

1. 作業者が事前に挙げた重要な判断5件のうち、4件以上を質問またはページに残せるか。
2. 追加回答を3分以内に終えられるか。
3. 主要主張の全てに根拠があり、原文・映像へ戻れるか。
4. 後輩が必要な判断に到達する時間を、既存の記録から探す場合と比較する。

これらは評価目標であり、達成実績ではない。実動画の専門家評価とiOS/Android実機確認は、自動テストの代わりにできない。

## 配布前の確認

端末内利用、認証付きAPI、チーム同期、AI応答、iOS/Androidでの撮影・保存・復元をそれぞれ検証する。ストア配布には署名、開発者アカウント、公開するAPI、サポート窓口、プライバシー表示、ストア用素材の確定と審査が別途必要になる。Capacitorの設定だけで申請可能と判定しない。

ベータを事前開発した事実と当日の作業範囲は [pre-event-disclosure.md](pre-event-disclosure.md) に残す。
